## 1. Problema

**O que vamos construir.** O repositório `banco` no GitHub, público, com:
- `go.mod` (o módulo Go), um `main.go` que imprime a versão e um teste passando;
- um `Makefile` com `test`, `lint` e `run`;
- o CI no GitHub Actions rodando em todo push: `go vet`, lint (golangci-lint), `go test -race`, build, `govulncheck` e gitleaks;
- README (o porquê do projeto), licença MIT e `docs/adr/0001-...` com a decisão de repositórios (um por sistema ou monorepo com `go.work`).

**Por que agora.** É o chão de todo o resto. A Fase 0 inteira (Dinheiro, Razão, concorrência) é Go puro com testes; sem o módulo, o `make test` e o CI, cada item seguinte começaria resolvendo ambiente em vez de domínio. O CI desde o primeiro dia é decisão do roadmap (§2, "Repositórios públicos"): os repositórios serão públicos, então o gitleaks tem de estar lá antes do primeiro segredo possível, e as fitness functions (§4) vão rodar nessa esteira (o depguard do 1.3, por exemplo).

**Onde encaixa.**
- **Antes:** nada. É o primeiro item.
- **Depende dele:** o 0.2 (Dinheiro sem float) já nasce como pacote dentro deste módulo, com teste rodando no CI; o estágio A0 do fio da arquitetura ("um módulo Go, só domínio e testes") é exatamente o que este item cria; o ADR 1 inaugura o `docs/adr/` que todo item de decisão vai usar.
- **A decisão escondida:** "um repositório por sistema ou monorepo" (ROADMAP §2 e §10) muda como `banco`, `spi`, `nuvem`, `escola`, `resiliencia` etc. vão se importar mais tarde. É a única escolha de verdade do item.

**Resumo da fase (23/11/2026).** O Lucas aceitou o objetivo da sessão (problema, diagnóstico e lista de estudo) e o tipo "prática com decisão curta". Pediu para explicar melhor a parte do tipo; a IA explicou que o processo curto (caminhos + decisão, sem tentativa ingênua nem checagem completa) vale **só** para a escolha de repositórios, e que o resto (go.mod, Makefile, CI) segue o modo prática. "Se importar depois" = um repositório usar código do outro (ex.: o `banco` importando a biblioteca `resiliencia`): com repositórios separados, por versão publicada (tag + `require` no go.mod); no monorepo com `go.work`, direto do disco, no mesmo commit.

## 2. Estudo
**Diagnóstico (23/11/2026)**, 4 perguntas sem consulta:
1. O que o `go.mod` guarda; módulo x pacote → **não sei**.
2. Como o CI sabe que `make test` falhou; se `go test ./... | tee saida.txt` esconde a falha → **não sei**.
3. Branch, pull request, merge x rebase → **sabe** (autodeclarado; confirmar na checagem).
4. GitHub Actions: workflow, job, step, gatilho → **não sabe**.

Tentativa ingênua: não se aplica (item de prática).

**O que estudar, nesta ordem** (teto: cerca de 1/3 do item; o resto sob demanda na execução):

| Fonte | Por quê (o que ela destrava) | Situação |
|---|---|---|
| T13 › Fundamentos › Por que Go e o ambiente | Instalar e usar o toolchain (`go run`, `go build`, `go test`, `go env`): sem isso não há `main.go` nem `make test` | a estudar |
| T13 › Pacotes, módulos e testes › Pacotes e visibilidade | A diferença entre pacote e módulo (pergunta 1): define onde fica o `main.go` e como o código se divide em pacotes | a estudar |
| T13 › Pacotes, módulos e testes › Módulos e dependências (+ go.dev "Tutorial: Getting started with multi-module workspaces") | O que o `go.mod` guarda, o `require` com versão e o `go.work`: é o que você precisa saber para decidir **como organizar os repositórios** (um por sistema, monorepo de um módulo, monorepo de vários módulos) na fase de caminhos | a estudar |
| T13 › Pacotes, módulos e testes › Testes de tabela e subtestes | O item pede um teste passando e o Lucas nunca escreveu teste em Go: destrava o `make test` | a estudar |
| T12 › Terminal e shell › Pipes, redirecionamento e exit codes | O CI decide verde ou vermelho pelo exit code (pergunta 2); um pipe pode esconder a falha. Destrava escrever o `Makefile` e os steps do CI sem falso verde | a estudar |
| T40 › CI com GitHub Actions › Workflows, jobs e cache | Workflow, job, step, gatilho (`on: push`) e cache (pergunta 4): destrava escrever o `.github/workflows/ci.yml` | a estudar |
| T40 › CI com GitHub Actions › A esteira de qualidade | O que entra na esteira (vet, lint, `-race`, build, gitleaks) e em que ordem: destrava o critério "CI verde em todo push" | a estudar |
| T21 cap. 21 · Decisões arquiteturais (consulta: só a parte de ADR) | O formato do ADR (contexto, decisão, consequências) para você escrever o ADR 1. O livro inteiro vem pela faixa | a estudar |
